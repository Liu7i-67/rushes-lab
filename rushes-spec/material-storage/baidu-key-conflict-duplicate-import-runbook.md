# 百度备份跨项目重复导入 key 冲突 处置手册

- 状态：可实施（依据 2026-10-09 key-conflict 周期既有机制 + 2026-10-20 dev 实战案例 4da4b1c1 整理）
- 日期：2026-10-20
- 适用：dev / prod（两环境 API 与前端行为一致）

## 1. 适用场景与症状判据

把**同一个百度源目录**备份到**第二个项目**（或任何「目标承接夹同名」的场景），第二任务准点启动后秒级终态 `failed`（`fail_reason=file_failed`）：

- 任务列表：状态「失败」，无传输发生；
- 任务明细：失败行 `last_error` 形如 **`key_conflict: 灵机备份/txlogo.png 已被 txlogo.png 占用`**；
- 行操作列只有【覆盖导入】【随机后缀导入】两条出路（普通「重试」被隐藏——原样重试必然再撞同一冲突）。

> 根因一句话：承接夹的物理对象键前缀 = 文件夹名（`灵机备份/`），**跨项目的同名承接夹共享同一物理键空间**；第一个任务先落库占用了 `灵机备份/txlogo.png`，第二个任务的同名文件在导入前行级预检被既有「跨资产 key 冲突保护」拦下。这是**刻意设计**（2026-10-09 key-conflict 周期）：直接落库会让两个资产静默共享/覆盖同一物理对象，宁可失败交用户决策。

## 2. 决策树（先定意图，再动手）

| 意图 | 做法 |
|---|---|
| 只是重复导了一遍，第二份不需要 | **不处理**。第一任务已把内容导入完成，失败任务可留档或删除 |
| **第二个项目确实也要存一份**（两处各持独立对象） | **方案 A（推荐）**：逐失败行「随机后缀导入」；文件多时用**方案 B**：删任务重建+换目标夹名 |
| 想让第二处「接管」这个文件 | 方案 C 覆盖导入——**跨项目场景禁用**，见 §5 红字 |

## 3. 方案 A（推荐）：随机后缀导入

逐个失败行改用随机后缀键重导，原占用者不动，两处各持独立对象（新文件名形如 `txlogo-a1b2c3.png`）。

**UI 步骤**：

1. 备份任务列表 → 打开失败任务明细；
2. 对每条 `key_conflict` 失败行，点操作列 **【随机后缀导入】**（提示「已用随机后缀重新导入」）；
3. 全部冲突行处理完后，任务自动复活入队（响应 202、状态 `enumerating`）；若同绑定无其他活动任务，下一拍派发执行（**等待节拍 ≤15 分钟**：10 分钟派发节流 + 5 分钟扫描周期），跑完剩余行后任务终态 `completed`。

**API 口径**（脚本化/排查用）：

```
POST /api/v1/baidu/backup/tasks/{task_id}/files/{file_id}/random-suffix
→ 202 {"finalized": true, "status": "enumerating"}
```

**适用边界**：仅 `key_conflict` 且 `non_retryable=false` 的失败行可操作；一条一行，多文件任务逐行处理（文件多时更推荐方案 B）。

## 4. 方案 B（文件多时）：删任务重建 + 换目标夹名

预防式根治：目标夹名不同 → 物理键前缀不同 → 天然不冲突，全部文件保持原名。

**步骤**：

1. 删除失败任务（明细页【删除】；删除会顺带作废其断点/清单行，已导入的第一任务资产不受影响）；
2. 在第二个项目里**先建好一个不同名的目标文件夹**（如 `灵机备份-项目B`），或在新建任务时**显式选择**一个不同名的既有文件夹——注意：**不选目标时系统会按源目录末段自动建同名承接夹，必撞**，所以本方案的关键就是「显式选不同名目标」；
3. 重建备份任务（同源目录 + 新目标夹）→ 排队执行至完成。

## 5. 方案 C：覆盖导入——本场景**禁用**

覆盖导入的语义是「**永久删除占用者资产**后按原名重新导入到本任务目标夹」。跨项目冲突时，占用者资产在**第一个项目**里——执行覆盖等于把文件从第一个项目**挪走**（第一处丢失），不是「两处都有」。仅当确认「这个文件本就该只存在于第二处」时才可用，且需要管理权限。

## 6. 验证清单（处置后逐项过）

UI：第二项目的目标夹里能看到文件（随机后缀名或原名）；任务状态 `completed`。

DB 抽验（dev 容器 `ms-db-dev` / prod 容器 `ms-db`）：

```sql
-- ① 两处资产各持独立对象（两个 asset id、两个不同 minio_key）
SELECT left(id::text,8) asset, filename, minio_key, folder_id
FROM assets WHERE filename LIKE 'txlogo%' ORDER BY created_at;

-- ② 任务终态与行级结果
SELECT status, count(*) FROM baidu_backup_task_files
WHERE task_id = '<task_id>' GROUP BY status;   -- 期望 success，无 failed
```

## 7. 常见问答

- **为什么不像网盘客户端那样自动改名？** 刻意交用户决策：静默改名/共享物理对象都违背「资产可追溯」；三种出路（后缀/换夹/覆盖）语义不同，各自适用不同意图。
- **同项目同夹重复备份会冲突吗？** 不会——同键同夹命中「已存在跳过」（`skipped_exists`），任务正常完成。冲突只发生在**跨夹/跨项目的同名物理键**。
- **排队中的任务多久开始？** 前序任务完成后 ≤15 分钟（10 分钟派发节流 + 5 分钟扫描周期），创建成功提示文案已注明。
